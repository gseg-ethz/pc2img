# Cross-AI Plan Review — Phase 03.1

## Codex Review

## Summary

Overall, the three-plan sequence is well-scoped for the phase goal: it separates evidence, in-tree disposition, and final sign-off, and most of the core repo assumptions check out. RRIM is not in the default feature barrel, the test imports it explicitly, `rrim.py` computes a 2-D RGB raster from slope/openness, the cuda extras pattern exists, CI has the 35% coverage gate, `LICENSE` exists, and the blocking todo exists. The main risks are packaging/verification gaps: adding a `pyproject.toml` extra without updating `uv.lock` may break frozen CI, the sign-off plan completes the blocking todo before human approval, and the automated grep checks are too weak to prove several legal/documentation claims.

## Strengths

- The D-11 default-barrel invariant is correct. [src/pc2img/features/__init__.py:1](/scratch/31_pc2img/src/pc2img/features/__init__.py:1) exports/imports the standard feature classes only; there is no `rrim` import through line 9.
- The opt-in import mechanism matches the current test path. [tests/test_rrim_features.py:5](/scratch/31_pc2img/tests/test_rrim_features.py:5) imports the registry and [tests/test_rrim_features.py:6](/scratch/31_pc2img/tests/test_rrim_features.py:6) imports `pc2img.features.rrim`, which triggers the decorators at [src/pc2img/features/rrim.py:460](/scratch/31_pc2img/src/pc2img/features/rrim.py:460), [src/pc2img/features/rrim.py:481](/scratch/31_pc2img/src/pc2img/features/rrim.py:481), and [src/pc2img/features/rrim.py:504](/scratch/31_pc2img/src/pc2img/features/rrim.py:504).
- The non-infringement premise is consistent with the code shape: `compute_rrim` rejects non-2-D inputs at [src/pc2img/features/rrim.py:351](/scratch/31_pc2img/src/pc2img/features/rrim.py:351), computes slope/openness/structure at [src/pc2img/features/rrim.py:355](/scratch/31_pc2img/src/pc2img/features/rrim.py:355), and `compose_rrim_rgb` stacks a flat RGB array at [src/pc2img/features/rrim.py:310](/scratch/31_pc2img/src/pc2img/features/rrim.py:310). I see no stereo/anaglyph/super-resolution path in this module.
- Plan 02 correctly models the new extra on the existing optional-dependency block at [pyproject.toml:51](/scratch/31_pc2img/pyproject.toml:51), where `cuda12` and `cuda11` are declared.
- Plan 03’s coverage-floor assumption matches CI: `--cov-fail-under=35` is present at [.github/workflows/ci.yml:46](/scratch/31_pc2img/.github/workflows/ci.yml:46), and CONTRIBUTING records the same floor at [CONTRIBUTING.md:74](/scratch/31_pc2img/CONTRIBUTING.md:74).
- The blocking todo exists and really is a publication blocker: [.planning/todos/pending/2026-07-09-rrim-patent-review-before-public.md:3](/scratch/31_pc2img/.planning/todos/pending/2026-07-09-rrim-patent-review-before-public.md:3), [line 25](/scratch/31_pc2img/.planning/todos/pending/2026-07-09-rrim-patent-review-before-public.md:25), and [line 52](/scratch/31_pc2img/.planning/todos/pending/2026-07-09-rrim-patent-review-before-public.md:52).

## Concerns

- **HIGH: Plan 02 changes `pyproject.toml` but omits `uv.lock` and lock verification.** The repo explicitly says any dependency edit must run and commit `uv.lock` at [CONTRIBUTING.md:86](/scratch/31_pc2img/CONTRIBUTING.md:86)-[92](/scratch/31_pc2img/CONTRIBUTING.md:92). CI installs with `uv sync --frozen` at [.github/workflows/ci.yml:35](/scratch/31_pc2img/.github/workflows/ci.yml:35)-[36](/scratch/31_pc2img/.github/workflows/ci.yml:36), so adding even an empty optional extra may create lock drift that the plan’s `uv run pytest` check will not catch.

- **HIGH: Plan 03 resolves the blocking todo before the human sign-off gate.** The todo says RRIM must not be pushed until investigated/resolved at [.planning/todos/pending/2026-07-09-rrim-patent-review-before-public.md:25](/scratch/31_pc2img/.planning/todos/pending/2026-07-09-rrim-patent-review-before-public.md:25)-[26](/scratch/31_pc2img/.planning/todos/pending/2026-07-09-rrim-patent-review-before-public.md:26). Plan 03 Task 1 moves it to completed while the sign-off record is still pending Task 2. If the owner raises concerns at the checkpoint, the planning state will already claim the blocker is completed.

- **MEDIUM: The “enable the `rrim` extra” wording is mechanically misleading.** Installing an empty extra does not import `pc2img.features.rrim`; only import-time registration adds the feature, as shown by the decorators at [src/pc2img/features/rrim.py:460](/scratch/31_pc2img/src/pc2img/features/rrim.py:460), [481](/scratch/31_pc2img/src/pc2img/features/rrim.py:481), and [504](/scratch/31_pc2img/src/pc2img/features/rrim.py:504). Since `features/__init__.py` does not import it, [src/pc2img/features/__init__.py:7](/scratch/31_pc2img/src/pc2img/features/__init__.py:7)-[9](/scratch/31_pc2img/src/pc2img/features/__init__.py:9), the docs should not imply the extra itself triggers registration.

- **MEDIUM: Plan 03 does not run the same command CI runs.** CI runs coverage with `uv run --frozen pytest --cov=pc2img --cov-branch ... --cov-fail-under=35` at [.github/workflows/ci.yml:42](/scratch/31_pc2img/.github/workflows/ci.yml:42)-[46](/scratch/31_pc2img/.github/workflows/ci.yml:46). Plan 03 runs only `uv run pytest tests/ -q` and greps the workflow. That proves the floor text is unchanged, not that the frozen install and coverage gate pass.

- **MEDIUM: The shipped legal docs may not actually ship in distribution artifacts.** The project has only a minimal `setup.py` calling `setup()` at [setup.py:1](/scratch/31_pc2img/setup.py:1)-[4](/scratch/31_pc2img/setup.py:4), `pyproject.toml` only references `LICENSE` at [pyproject.toml:10](/scratch/31_pc2img/pyproject.toml:10), and I found no `MANIFEST.in` or package-data rule. The files will ship in the repo, but the plans do not verify whether `NOTICE` and `docs/ip/rrim-ip-findings.md` are included in sdist/wheel.

- **LOW: The grep gates are too easy to satisfy accidentally.** Plan 01’s check for independent-claim analysis can pass with one generic “claim 1” or “accepted residual” mention, not one section for each active patent. Plan 03 checks that the sign-off file references `rrim-ip-findings.md`, but not that it references `NOTICE`, despite that being acceptance criteria.

- **LOW: The plan says to edit RRIM class docstrings, but the classes currently have none.** `RRIMPackFeature`, `RRIMFeature`, and `RRIMComponentFeature` begin at [src/pc2img/features/rrim.py:460](/scratch/31_pc2img/src/pc2img/features/rrim.py:460), [481](/scratch/31_pc2img/src/pc2img/features/rrim.py:481), and [504](/scratch/31_pc2img/src/pc2img/features/rrim.py:504) without docstrings. This is easy to handle, but the plan should say “add/update” rather than “edit wording.”

## Suggestions

- Add `uv.lock` to Plan 02 `files_modified`, run `uv lock`, and verify with `uv lock --check` plus the CI-equivalent `uv run --frozen pytest ...`.
- Move the blocking todo only after Task 2 approval, or keep it pending with a “prepared, awaiting sign-off” note until the human checkpoint passes.
- Change RRIM docs to say: install/use the `rrim` extra for signposting if desired, but callers must still `import pc2img.features.rrim` before `generate(["rrim"])`.
- Replace Plan 03’s test command with the CI command, including `--frozen`, coverage, and `--cov-fail-under=35`.
- Add a packaging verification step: build sdist/wheel and inspect that `NOTICE` and the intended IP findings doc are included, or explicitly configure inclusion.
- Strengthen grep checks into targeted assertions for both active patents, `NOTICE` in the sign-off file, and absence of planning IDs in shipped files.

## Risk Assessment

**Overall risk: MEDIUM.** The conceptual plan is sound and most repo mechanics validate cleanly, but the lockfile/CI gap and premature todo completion are material process risks. Fixing those two, plus clarifying that extras do not auto-register RRIM, would make the phase plan low risk. I could not run pytest in this environment because the filesystem is read-only and `uv` could not create its cache lock file.
