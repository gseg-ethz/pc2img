plan was written, and both proposed fixes were verified end-to-end before it was written:

- **G9** — `RRIMConfig.pack_feature_name()` formats `z_factor` with a general-format call that emits
  exponent notation below 1e-4 and truncates to 6 significant figures, while `_Z_FACTOR_RE` accepts
  neither. Reproduced: `z=1e-05` -> pack name `rrim_pack_(range,r16,d8,z1e-05)` ->
  `FEATURES.match(...)` raises `ValueError: Unknown RRIM option 'z1e-05'`; `z=1.2345678` silently drifts
  to `1.23457`. **Beyond the UAT record:** the truncation also makes the cache key **non-injective** —
  `z=1.2345678` and `z=1.2345681` collide on the identical name `rrim_pack_(range,r16,d8,z1.23457)` and
  therefore share one cached raster. Blast radius is small and confirmed: `_format_number` has exactly
  ONE call site (`rrim.py:70`, z_factor only) and is not shared with any other feature-name grammar.
- **G10** — `DiskBackedImageStore.__delitem__` unlinks the on-disk codec pair BEFORE `super()` validates
  key membership, so a `KeyError`-raising delete still irreversibly destroys the files. **Worse than the
  UAT record:** with two stores over one cache dir, `del A["range"]` raises `KeyError` and destroys the
  raster that store **B** owns — B had cleared its in-memory reference on offload, so B itself can no
  longer serve the key. This is live data loss in the owning store, not merely a stale-cache-recovery
  concern, and the proving test must assert that stronger property.

Neither defect is reachable by the current 135-test suite: the round-1 G1 end-to-end RRIM tests all use
default-ish `z` values (which is precisely why they pass today and why this regression class was
invisible), and no test exercises a cross-store delete. CI on PR #12 is green with both defects present.

Rationale the owner accepted (verified before writing this plan — cite it in BC entry 14): switching to
shortest-`repr` leaves the emitted token **byte-identical** for every z value that works correctly today

1.2345678; `3.33333` from 3.3333333333). Cache-key churn is therefore ~zero and is paid only where the
key is currently WRONG. Full precision is retained: the 6-significant-figure limit is FIXED, not
documented around.

Also settled: `z_factor` is a plain scale multiplier (`raster * z_factor`, validated `> 0`), so sub-1e-4
values are legitimate unit conversions (um -> m = 1e-06). Do NOT plan or implement a "reject small z" shape.
