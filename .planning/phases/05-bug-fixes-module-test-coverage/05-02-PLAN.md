<perspective_api_contract>
## PerspectiveProjection public contract (M-02/M-03/M-04 — DECIDED)

Decided in the 05-REVIEWS cross-AI follow-up (Codex HIGH concern #1). This pins the public API so
the executor implements it directly rather than re-deriving it. **Supersedes** the "if the caller
pre-bakes `t`, document instead" fork in Task 3 and the RESEARCH §"Open Questions" #3 empirical
resolution. Evidence: no on-disk checkout (`/scratch/{31_pc2img,41_pchandler,30_GSEGUtils}`)
constructs `PerspectiveProjection` — the 4×4 path has zero reachable callers.

### Signature
`PerspectiveProjection(projection_matrix, rotation_matrix, *, translation=None)`
- `projection_matrix` (K): **unchanged** — 3×3 intrinsic, applied linearly; the perspective divide
  stays manual (`uv[:, :2] / uv[:, 2]`).
- `rotation_matrix` (R): **must be a 3×3 proper rotation** (see Validation). Meaning unchanged.
- `translation` (t): **NEW**, keyword-only, length-3 vector, default `None`. `None` → `zeros(3)` →
  reproduces today's exact origin-camera behavior. This is the only change existing 3×3 callers
  see: none (they keep `t=0`).

### Camera model & convention
Full pinhole `x ∝ K·(R·X + t)`, **camera-frame** translation convention — matching pchandler
`Transform.generate(rotation, translation)`, which builds `x0 = (R·s + t) @ x1`
(`transforms.py:195-208`). Document in the class docstring: a caller holding a camera *center* C
(world coords) passes `t = −R·C`. Do NOT invent an `R·(X−C)` convention.

### Implementation direction — extrinsic-FIRST (required)
`pcd.__rmatmul__` accepts a 4×4 only if it is a pure affine (bottom row `[0,0,0,1]`); a projective
4×4 raises (`coordinates.py:194-198`). And `_TransformArray.__matmul__` composes only same-shaped
matrices (`transforms.py:62`). So K (3×3) **cannot** be pre-composed with a 4×4 extrinsic — do NOT
write `(K @ extrinsic) @ pcd`. Instead:
  1. `extrinsic = Transform.generate(rotation=R, translation=t)`   # 4×4 affine [R|t]
  2. `Xc = extrinsic @ pcd`                                        # camera-frame coords (N,3)
  3. apply K to `Xc`, then perspective-divide by depth `Z_c`
M-02 depth cull operates on `Xc`: mask `Z_c > 0` (drop behind-camera points) at/around the divide.

### Validation (fail-fast in `__init__`, per the eager-constructor-validation convention)
- `rotation_matrix` must be shape `(3,3)` **and** orthonormal: `np.allclose(R @ R.T, I, atol=1e-6)`
  and `np.isclose(np.linalg.det(R), 1.0, atol=1e-6)`. A non-orthonormal 3×3 (scale/shear baked in) →
  **raise ValueError** (silently honoring it is the silent-wrong-geometry bug class this project
  rejects). Tolerance `atol=1e-6`; loosen only if a real scanner-derived R legitimately fails.
- Any non-3×3 `rotation_matrix` (notably a 4×4) → **raise TypeError**:
  `"PerspectiveProjection expected a 3×3 rotation matrix; got shape {shape}. Pass the camera
  translation via the translation= argument."`
- `translation`, when not None, must be a length-3 vector → else ValueError.

### Breaking-change stance (no runtime DeprecationWarning)
Rejecting a 4×4 `rotation_matrix` is a breaking change, **intentionally batched** into this
already-breaking release. NO `warnings.warn(..., DeprecationWarning)`: the 4×4 path was never a
working, documented contract, so there is nothing to "deprecate"; version pinning is the deferral
mechanism for any off-disk caller that can't migrate yet. The obligation is (a) the actionable
TypeError above and (b) the D-17 changelog/BC note — not a runtime warning.

### Registry / coercion path
`PerspectiveProjection` is `@PROJECTIONS.register("perspective")` (`projection.py:192`). The new
`translation` kwarg must survive the `(name, kwargs)`-tuple / pydantic `validate` coercion and the
registry kwarg-filter. Add a test that tuple/`make_generator` construction with `translation=`
works — not just direct `__init__`.
</perspective_api_contract>
