<objective>
Close G1-CR-01 and G1-WR-04, and bring the tiled docstring parts those fixes own in line (the G1-IN-03 wording). Round 1 stopped the crash but did not deliver readable output: every pickle round-trip of a tile generator gives the parent another entry object on the same `<tile>/<key>.dat` with its own armed GC finalizer, so when call N's results are released after call N+1 ran (ordinary rebinding, `result = gen.generate(...)`), their finalizers unlink the files call N+1's entries read lazily — `np.asarray(result[...])` raises `FileNotFoundError` (planner reproduction 2026-10-02 on HEAD `7094dde`: `n_jobs=2` fails 3 of 3 at the read, `n_jobs=1` reads 3 of 3). The round-1 regression test never read an array, so it passed. Fix on the pc2img side as the owner decided: after reassembly, call the public `LazyDiskCache.disable_purge()` on every returned entry and every live entry of every reassembled store when the work ran in a pool. Accepted cost (owner decision 2026-10-02, tracked by a todo the orchestrator writes — this plan creates no todo file): after a pooled run the `.dat` files persist on disk until `purge()` or removal of the cache directory, including the default `tempfile.mkdtemp` directory a store creates when no `cache_path` is configured; the class docstring and BC-P2I-030 state this prominently with the routes. GSEGUtils' own-file-only finalizer is backlog, not this round. Separately, duplicate tile ids are accepted today and make later calls hand one generator to two tasks (one tile silently computed from another's points, one tile dropped from the results, and the GSEGUtils#82 race back in a pool): reject them at construction.
